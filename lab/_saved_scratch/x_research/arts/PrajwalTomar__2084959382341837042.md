# Claude Code Subagents Are CRACKED Now. Here's My Exact Workflow.
Most people just unleashed a swarm of subagents, watched it burn through context and money, and decided nested agents are a gimmick.
Some capped it at one layer, so their "team" is really one agent doing everything in sequence, no faster than before.
And then there is a small group who run an actual structure: one lead, a scoped team, a review fan-out, and cheap models doing the volume. Those are the people shipping real features in a single prompt.
I run an AI agency and I have taught 3,500+ people to build with AI, and agent workflows are how we ship client MVPs faster every month. When Claude Code reopened nested subagents, I rebuilt our setup around it. This is the exact system, and the mistakes that waste most people's runs.
Here is the full breakdown.
## What Actually Changed
Claude Code just reopened nested subagents. A subagent can now spawn its own subagents, up to three layers deep by default, up from a hard limit of one. Opus 5 is the default model, with a 1M-token context.
That sounds small. It is not. Depth 1 meant a subagent could not delegate at all, ask it to spin up helpers and it just did the work itself, in one context window. Depth 3 means you can hand off a whole slice of a project and let the tree organize itself.
There are two knobs that matter, and most people never touch them:
- `CLAUDE_CODE_MAX_SUBAGENT_SPAWN_DEPTH` controls how deep the nesting goes. Set it to 1 for flat, single-layer delegation.
- `CLAUDE_CODE_MAX_CONCURRENT_SUBAGENTS` caps how many run at once. It defaults to 20, so one message can fan out a lot of background agents fast.

## The Problem With How Most People Use Subagents
The default instinct is to unleash as many agents as possible and hope. That fails three ways.
No orchestrator. If every agent can spawn siblings freely, nobody owns the plan. They drift, duplicate work, and quietly overwrite each other's changes.
Context and money burn. Twenty concurrent agents on Opus 5 each carry their own context. You will watch your usage and your bill spike, for work a smaller setup does cleaner.
No verification. A swarm that writes code is not a team. A team has someone checking the work against the plan. Without that, you ship whatever the loudest agent produced.
The fix is not fewer agents or more agents. It is structure.
## The Setup, Step by Step
## Step 1: One orchestrator owns the plan
Before any agent runs, the lead agent writes the plan and owns it. Subagents execute pieces of that plan, they do not freelance new work. This single rule kills most of the drift people blame on the model.
[media One orchestrator plans, then spawns scoped subagents while a reviewer verifies each finding against the plan.]
## Step 2: Use depth 3 as a review fan-out, not a free-for-all
Depth 3 was chosen deliberately. It is exactly what a review needs: the main conversation spawns a reviewer, the reviewer spawns one verifier per finding, and each verifier can still run a focused lookup. That is the shape to build toward. Going deeper than the work actually needs is where agents start eating their own context.
[media What changed in Claude Code 2.1.219: nested subagents now run three layers deep by default, on Opus 5.]
## Step 3: Scope every subagent to one job
Give each agent a tight brief: "write the tests for this module," not "improve the codebase." Vague scope is the single biggest cause of wasted tokens. A scoped agent finishes and reports. A vague one wanders.
## Step 4: Cap the fleet on purpose
Do not run 20 agents because you can. Lower `CLAUDE_CODE_MAX_CONCURRENT_SUBAGENTS` to what the task needs, and set `CLAUDE_CODE_MAX_SUBAGENT_SPAWN_DEPTH` to 1 when a workflow assumes a flat structure. Constraints are what make the output legible.
[media Depth 3 as a review fan-out: the main conversation spawns a reviewer, which spawns one verifier per finding.]
## Step 5: Cheap models on the workers, flagship on the lead and reviewer
This is the money move. Put Opus 5 where judgment matters, the lead that plans and the reviewer that checks. Let the workers doing volume run on a cheaper model. Same output on the parts that eat tokens, a fraction of the bill.
[media The two knobs in settings.json: how deep subagents nest, and how many run at once.]
## When to Use Depth 3 vs Flat
Use the depth-3 review fan-out when the task genuinely branches: a build with independent modules, a review pass with several findings, a migration with parallel steps.
Stay flat (depth 1) when the work is sequential, or when a workflow assumes a single fan-out. Deeper is not better. Deeper is more coordination cost. Match the structure to the shape of the work.

## What To Watch Out For
A few honest flags before you rebuild your setup.
Context and cost scale with the tree, not the task. More agents is more context carried in parallel. Cap concurrency deliberately.
Subagents drift without a plan. If the lead does not own a written plan, the tree will quietly diverge from what you asked for.
Nesting is not review. A verifier only helps if it checks against the plan. Wire the verification in, do not assume depth alone gives you quality.
Watch the knobs after updates. Claude Code has changed the default spawn depth a few times in a few weeks. Pin `CLAUDE_CODE_MAX_SUBAGENT_SPAWN_DEPTH` in settings so an update does not silently change your topology.
